## 一、总体印象

这六个文件构成 MARS-408 的"算法门面"——也是申报书 Table 2-2 全部创新点的落点。**整体质量明显高于项目平均水平**，是团队踩坑史（torch 静默崩溃、embedding 维度静默归零、RL 假有效、互补事实误报）沉淀最密集的区域。亮点集中在：

1. **失败路径 fail-open 极其成熟**——所有 LLM/torch/检索失败都安全降级（规则平均、BM25-only、随机权重、人工审核），不会阻断流水线或启动。
2. **误报防御精细**——`gomarl_conflict.py` 的逗号切句 + 否定词排除，专门防"路由器在网络层，交换机在数据链路层"这类互补正确事实被误判为矛盾；`frugal_rag.py` 的 `RERANK_POOL=60` 修掉了"先截 top-k 再重排导致漏召回"的经典架构坑。
3. **踩坑经验已固化进注释**——`gomarl_mixer.py` 的 `_ensure_torch` global 变量修复 `UnboundLocalError`（注释自述根因），`frugal_rag.py` 的 Reranker 离线优先 + 失败永久禁用，都是用事故换来的防御。

需要补强的是**跨模块关注点分离（私有 API 耦合）**与**几处"文档宣称 ≠ 实际接线"的语义落差**——这些 CI 抓不到、评审/维护阶段才会暴露。

## 三、问题清单（按优先级）

### 🔴  blockers：无

### 🟡  应当修复（suggestion）

**C1 · mixer 的 `self._embed_dim = 384` 默认值与注释矛盾，是诱导错误修复的 footgun**
- 位置：`gomarl_mixer.py:369-371`（注释"当前为 768=e5-base-v2"，但默认值写 `384`）
- 问题：注释与代码打架。维护者若信了默认值去"对齐"，会把 net 输入维度改成 384，而 `AgentOutputEncoder` 仍喂 768 维 E5 向量 → `hyper_w1[i](agent_embeddings[i:i+1])` 形状不匹配，训练权重静默落回随机权重（注释 L66 自述过的根因会重演）。
- 建议：默认改为 `get_embedding_config().get("dimension", 768)` 或从 `self.encoder.dim` 派生；注释改为"死默认值，生产由 probe/config 覆盖为 768"。

**C2 · mixer ONNX 推理路径输入形状双重赋值 + 契约未文档化（静默 shape 风险）**
- 位置：`gomarl_mixer.py:590-602`
- 问题：先 `scores_np = scores.reshape(1,-1)` / `emb_np = embeddings.reshape(1,n,-1)`，紧接着在 `if len(scores.shape)==1` / `if len(embeddings.shape)==2` 分支里又把同一个 key **覆盖回** `(n,)` / `(n,768)`。第一段 reshape 是死代码；最终传入 ONNX 的形状取决于"原始形状"，而 ONNX 模型到底期望 `(1,n)`+`(1,n,768)` 还是 `(n,)`+`(n,768)` 全程无文档。一旦不匹配，ONNX Runtime 抛错被 `except` 吞掉 → 静默降级规则平均，神经网络"看起来用了其实没用"。
- 建议：删除死 reshape，明确 ONNX 导出契约（在 `_ensure_onnx` 处补模型输入 shape 注释），并加一次启动期 shape 自检断言。

**C3 · 冲突引擎"语义级检测（E5 向量）"在两条调用链均不可达（文档宣称 ≠ 实际接线）** ⚠️ *复核后升级：非仅 API 路径*
- 位置：`gomarl.py:476`（**图管线** `_check_consistency_enhanced` 调 `check_and_resolve(agent_dicts, course=course)`，不传 `agent_embeddings`） + `api/engine.py:135-137`（**API 端点**同样不传） + `gomarl_mixer.py:557`（docstring 列 `agent_embeddings` 为 `mix()` 返回值） vs `648-656`（**实际返回 dict 不含该字段**）
- 问题：`ConsistencyChecker.check` 的语义级分支（L284 `if agent_embeddings is not None`）需要 embeddings；但**图管线与 API 端点两条链都不传**（`mix()` 也不返回它，无从获取）。结果 headline 功能"语义级冲突检测：E5 向量余弦相似度（替代关键词匹配，升级为语义级）"在**生产全路径从未执行**，仅事实级 + 跨 Agent 矛盾对检测生效。这是评审对创新点最敏感的区域，建议尽快接通或降级宣称。
- 建议：① 在 `gomarl.py:_check_consistency_enhanced` 与 `api/engine.py:gomarl_consensus` 内用 `neural_mixer.encoder.encode_batch(texts)` 重编码并显式传入 `agent_embeddings`；② 接通前必须先收紧 C10（阈值假阳性），否则会把"不同主题的正确内容"大量误报为语义冲突并污染 `flagged_agents`。若不愿承担该行为变化，则在 docstring / 申报口径中将"语义级检测"标注为"离线/实验能力，默认关"。

**C4 · 冲突消解统计用字符串包含统计 `resolved_count`，漏判变体**
- 位置：`gomarl_conflict.py:636-638`（`"需人工审核" not in c.resolution`）
- 问题：LLM 若返回"需要人工审核""转人工审核""无法判断，人工审核"等变体，子串匹配漏判 → 被误计为已消解。计数口径脆弱。
- 建议：定义 `ResolutionEnum`（A正确/B正确/综合修正/需人工审核/消解失败）常量，统计按枚举而非子串。

**C5 · 贪婪 JSON 提取 `re.search(r'\{.*\}', reply, re.DOTALL)` 重复两处，易误抓**
- 位置：`gomarl.py:_score_single`(约 L281) + `gomarl_conflict.py:_llm_resolve`(L576)
- 问题：贪婪匹配会抓到正文/evidence 中最外层 `{...}` 而非 JSON 块本身；若 LLM 在 JSON 外裹了 markdown 代码围栏或正文含大括号，解析错位 → `json.loads` 失败 → 整条降级。同一反模式跨文件复制。
- 建议：抽共享 `extract_first_json(reply)`（处理 ```json 围栏、定位首个 `{` 到配平 `}`，失败返回 None），两处复用。

**C6 · 跨模块私有 API 耦合 `teaching_rules._dependencies` / `_agent_affinities` / `_match_chunk_to_topic`（系统性 🟡）**
- 位置：`frugal_rag.py`(531/596/602/614)、`frugal_rag_sft.py`(458-538 多处)、`gomarl.py`(334/337/349/366/390/396)、`gomarl_mixer.py`(707/723)、`api/engine.py:286`——共 5 文件 20+ 处。
- 问题：调用方直接读 `teaching_rules._dependencies`（下划线私有）与内部 `_agent_affinities`、`_match_chunk_to_topic`。`teaching_rules` 一旦重构内部字段名/结构，所有这些点会**静默断裂**（属性访问不抛 `AttributeError` 的场景下返回 None，进而逻辑错乱而非崩溃）。`engine.py:286` 甚至在 API 层直接 `teaching_rules._dependencies.get(topic_id)`，与同文件 L285 已提供的公开 `get_cross_subject_prerequisites` 不一致。
- 建议：为 `teaching_rules` 增加公开方法 `get_dependency(topic_id)` / `iter_dependencies()` / `get_agent_affinity(name)`，内部调用方与 API 层统一改走公开接口。

**C7 · gomarl `_trace_flagged_agents` 用 `r.agent_name in issue` 子串匹配，可能误命中**
- 位置：`gomarl.py`（约 L443，`_trace_flagged_agents`）
- 问题：当某 agent 名恰好是另一条 issue 文本的子串时（如 agent 名 "tcp" 命中含 "tcp" 的 issue），会错配责任归属。
- 建议：用结构化字段（issue 携带 `agent` 列表）匹配，或要求 `issue` 包含完整 token 边界（正则 `\b{name}\b`）。

**C8 · gomarl `_neural_mix` 失败返回 `consensus_score=0`，与"真实低分"不可区分**
- 位置：`gomarl.py`（`_neural_mix` 失败分支）
- 问题：神经网络混合异常时返回 `consensus_score=0`，上层难以区分"Agent 产出确实很差（0 分）"与"神经网络故障降级失败"。可能误导决策（如触发 regenerate 风暴或错误 manual_review）。
- 建议：返回显式哨兵（如 `neural_failed=True` 或 `consensus_score=None`），上层据此选择是否回退规则平均并打日志告警。

**C9 · `require_llm_quota` 装饰整个 engine router，只读观测端点也消耗 LLM 配额**
- 位置：`api/engine.py:22`（`dependencies=[Depends(require_llm_quota)]` 挂在 router 级）
- 问题：`/status`、`/teaching-rules`、`/stop-decision`、`/neural-mixer`、`/lora-config` 均为只读可观测端点，不调 LLM，却被统一扣 LLM 配额。前端监控面板/轮询会无谓耗尽配额，甚至在正常观测下触发 429。
- 建议：把配额依赖从 router 级下移，仅挂到真正调 LLM 的端点（`/frugal-rag-full`、`/gomarl-consensus`、`/conflict-check`、`/teaching-rules/validate` 等写/计算端点）。

**C10 · 语义冲突检测阈值启发式，假阳性风险高（与 C3 联动）**
- 位置：`gomarl_conflict.py:188`（`_SEMANTIC_CONFLICT_THRESHOLD = 0.3`）+ `_check_semantic`(393-415)
- 问题：`sim < 0.3` 且双方内容 >100 字即报"语义冲突"。但两个**不同主题的正确内容**（如 Teacher 讲 TCP 握手、QuizMaster 列 UDP 事实）余弦相似度同样很低 → 被误报为冲突。当前因 C3 未接入 API 而"侥幸安全"，一旦接通必须先收紧（如仅对"同知识点不同断言"的句子对检测，或抬升阈值 + 要求事实层已命中）。
- 建议：语义检测前置"同 topic/同实体"约束，或改用相对相似度差而非绝对阈值。

**C11 · mixer 共识分 ×10 量纲映射依赖 net 输出在 [0,1]，但 `global_mixer` 无激活约束**
- 位置：`gomarl_mixer.py:612` / `624`（`consensus_score = max(0, min(10, float(cs)*10))`）
- 问题：`global_mixer` 末层是 `nn.Linear(hidden_dim, 1)` 无激活，输出可为任意实数。`×10` 再钳制 [0,10] 的假设是"net 输出≈[0,1]"。若训练未把输出约束到该区间，×10 会越界被钳，丢失 net 的真实信号（且注释称旧逻辑"拉满恒 1.0"，新逻辑仍依赖隐含约定）。
- 建议：对 net 输出做 `sigmoid`/`tanh` 归一或显式文档化训练约束；或直接让 net 输出 1-10 量纲、去掉 ×10。

### 💭  nice to have（nit）

- **N1（graph.py）**：模块 docstring 与多处注释标"10 节点"，实际 `add_node` 调用 **11 次**（含 triage 入口）。项目 memory 已记口径统一为 11。建议把注释的"10 节点"改为"11 节点"，与代码一致（避免评审/后人按 10 数节点）。
- **N2（mixer）**：`NeuralGroupMixer.__init__`(L343) 直接 `get_gomarl_config()` 无 try/except，模块导入期若配置未就绪会抛错导致整个模块导入失败；对比 `AgentOutputEncoder.__init__` 有 try/except 保护。建议统一加保护或延迟到首次 `mix()`。
- **N3（conflict）**：`EvidenceConflictResolver._checker` 实例从未被使用（`resolve` 走 engine 级 `checker`），属死代码；且 `ConsistencyChecker` / `EvidenceConflictResolver` 各 new 一个 `LLMProvider()`。建议删 `_checker` 或复用单例。
- **N4（frugal_rag）**：`retrieve`(约 L465) `result[0]['score']` 尽管前面有 `if not candidates: return []` 保护，但属脆弱点（后续重构若去掉保护即 `IndexError`）。建议加 `if candidates:` 守卫或取 `max(candidates, key=score)` 而非 `[0]`。
- **N5（mixer）**：`forward` 的 `sd_loss` 用 Python 双层 for + 每对 torch 算子（O(n²) 非批处理）。n≈6 可忽略，但属可向量化点。
- **N6（conflict）**：`check_and_resolve` 一致性公式 `1 - conflicts/max_possible`，`max_possible` 是 pair 数（n(n-1)/2），但 factual（intra-agent）错误也计入分子、却不在"pair"分母假设内 → 轻微低估不一致度。建议分母改为"实际执行的检测数"。

## 五、标准自检：本次审查暴露《代码审查标准.md》需补强的点

## 六、下一步建议

1. **优先处理 C3（语义检测不可达）**：它直接关系评审对"语义级创新"的核验。要么在 `gomarl_consensus` 端点接通 embeddings，要么在申报口径显式降级——**不能让"已实现的语义检测"停留在只接通事实层的状态**。

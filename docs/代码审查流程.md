# 代码审查流程（Code Review Process）

> 配套文档：[代码审查标准](./代码审查标准.md)（查什么）｜ PR 模板：`.github/PULL_REQUEST_TEMPLATE.md`
> 本流程遵循既有架构治理（ADR-007/008/009/011/015/017），把"人工审查"嵌入双分支双身份的协作模型。

---

## 1. 角色与职责

| 角色 | 职责 | 权限 |
|------|------|------|
| **作者（Author）** | 写代码、填 PR 模板、本地自检、回应审查意见、标记 addressed | 发起 PR |
| **审查者（Reviewer）** | 按[标准](./代码审查标准.md)审查，给分级意见与结论（Approve / Request Changes / Comment） | 提意见、请求改动 |
| **把关人（Maintainer / 架构师）** | 合并权；对红线/ADR 冲突一票否决；裁决分歧 | 合并 / 驳回 |

**小团队现实（本项目）**：作者自检 + **至少 1 名交叉审查者**；把关人只审**红线文件与跨分支影响**，不逐行审全部 PR，避免瓶颈。交叉审查者熟悉对应模块即可。

---

## 2. 双分支工作流

- **禁止直推受保护分支**：`main`（MARS-408，冻结）不接受直接 push；`career-literacy`（芒得很职，活跃）经 PR 合并。
- **标准路径**：`feature/xxx` 分支 → 开 PR（目标 `career-literacy` 或 `main`）→ 审查 → CI 全绿 + 审查结论 → 把关人合并。
- **跨分支同步**：仅 `main → career-literacy` **单向**同步；不可逆。career 改动**不得回写** `main`。
- **并发会话纪律**：多 AI 会话/多人同仓时，提交前**只 `add` 自己的文件**，勿 `git add .` 扫入他人改动（见标准 §2.3④）。

---

## 3. 何时必须审查（触发条件）

以下 PR **必须**走完整审查，不得跳过：

1. 所有进 `main` / `career-literacy` 的 PR（本地实验分支可宽松）。
2. **触碰红线文件**（命中即重点审）：
   - 后端：`engines/review_policy.py`、`main.py`（安全中间件）、`engines/gomarl_conflict.py`、`shared/prompt_guard.py`、`db/*`、`llm_provider.py`、`services/import_worker.py`
   - 前端：`src/utils/api.ts`、`src/composables/useBenchmark.ts`、任何 `v-html` 使用点
3. **任何评测/诊断脚本新增或修改**（ADR-017 硬纪律：须与生产同口径）。
4. **新增 `career_*` 模块或路由**（ADR-015 零侵入公约）。
5. 涉及密钥、迁移、LLM 通道优先级、并发模型的改动。

---

## 4. 作者提交前自检清单（PR 前必过）

- [ ] **本地 CI 三件套通过**：`pytest` 离线集（Linux/CI 或本地分文件）｜`npm run type-check` + `npm run lint` + `vitest` ｜ `npm run build`
- [ ] **红线自查**（对照标准 §0 速查表 + §2）：无 `except pass`、无裸 `fetch`、无合成兜底数字、未改 embedding/单写者/CSP/动词门控
- [ ] **安全自查**：无密钥提交、端点鉴权未缺失、`v-html` 过 DOMPurify
- [ ] **变更最小化**：不夹带他人文件、不混入无关重构
- [ ] **测试证据**：关键改动有对应测试，且（如适用）做了变异验证
- [ ] **描述充分**：PR 模板已填，关联 ADR/issue，说明风险与回滚

---

## 5. CI 门禁联动

**现有 CI（已落地，审查前置条件）**：
- `backend-test.yml`：Linux 离线单元/集成/E2E（`-m "not system and not requires_milvus and not slow"`），权威回归看 Linux。
- `p0-regression.yml`：**P0 用例最先跑且不可失败**；fast-unit（Win+Linux 矩阵 + 覆盖率 ≥50% + per-file 门禁）；nightly 跑 slow。
- `ci.yml`：前端 `type-check` / `lint` / `build` / `vitest`。

**新增建议（把标准 §2 红线变成自动守护）**：
- **红线 grep 守护**（轻量 CI 步或可本地 pre-commit）：
  - `engines/review_policy.py` 外出现 `def discipline_gate` / `def review_precision` → 失败（ADR-017）。
  - career 改动出现非 `career_*` 前缀的新增模块/路由且改了 408 源文件 → 失败（ADR-015）。
  - 前端 `src/**` 出现裸 `fetch(`（排除 `utils/api.ts` 与 worker CDN 拉取豁免）→ 失败（标准 §2.2②）。
  - 提交中出现 `.env` / `config.json` / `*.db` → 失败。
- **覆盖率门禁**：沿用 `cov-fail-under=50` + per-file 阈值脚本，防止关键模块掉覆盖。

> **关键认知**：**CI 绿 ≠ 可合并**。红线违反、设计缺陷、口径漂移、合成兜底等问题 CI 抓不到，必须靠人工审查（标准 §2/§3）。审查结论是 CI 之外的第二道闸。

---

## 6. 审查轮次与裁决

- **时效**：首轮审查在 PR 发起后 **48h 内**给出；小 PR（<200 行）优先快审。
- **结论三态**：
  - ✅ **Approve**：无 🔴、🟡 已处理或已豁免，可合并。
  - 🔴 **Request Changes**：存在任一 🔴 阻断项，必须修改后重审。
  - 💬 **Comment**：仅有 💭 建议或讨论，不阻塞合并（作者酌情采纳）。
- **红线冲突**：把关人可直接 Request Changes 并**引用 ADR/CLAUDE 条款**，无需二次确认。
- **收敛**：作者改完在对应意见下标记 "addressed"；审查者复核后解除 🔴。多轮未收敛由把关人仲裁。
- **互斥保护**：同一 PR 在审查中/CI 跑重时，避免并行 Agent 同时重算/重跑 pytest 互踩向量库（见记忆·并行 Agent 病）。

---

## 7. 质量度量与持续改进

- **跟踪指标**（把关人季度回顾）：
  - 每 PR 红线违反数（按 §0 分类）
  - 平均审查轮次、首轮响应时效
  - CI 红率 / P0 回归失败次数
  - 反复出现的 🟡/💭 主题
- **改进闭环**：反复出现的问题 → 写进标准 §2/§3 或升级为**新 ADR**（如某反模式稳定复现即固化为红线）。
- **本机制本身**登记为 `ADR-018`（见 `docs/adr/ADR-018-code-review-mechanism.md`），随治理演进更新。

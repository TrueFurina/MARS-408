# ADR-018 — 代码审查机制（标准 + 流程 + PR 模板）

- **状态**：Accepted
- **日期**：2026-09-15
- **决策人**：架构师（architect）
- **相关**：ADR-007（单写者）/ ADR-008（并发模型）/ ADR-009（LLM 通道）/ ADR-011（评审权重 MAPPO 化）/ ADR-015（双分支治理）/ ADR-017（评审单一真值源）；`CLAUDE.md`
- **关联文件**：`docs/代码审查标准.md`、`docs/代码审查流程.md`、`.github/PULL_REQUEST_TEMPLATE.md`

## 背景

本仓库已有成熟的**架构决策治理**（ADR-007~017 + `CLAUDE.md` 硬约束 + 三套 CI：`backend-test` / `p0-regression` / `ci`）。但"人审代码"环节此前无统一标准：审查者凭感觉、红线（embedding 硬约束、单写者、分支零侵入、判定语义单一真值源、前端数据可溯源等）依赖个人记忆，易在并发多会话开发中漏检。代码质量参差不齐的直接诱因之一，是**缺少把既有 ADR/CLAUDE 决策落到 PR 审查环节的系统化机制**。

## 决策

1. **建立三层审查资产**，作为所有 PR 的人工审查依据：
   - `docs/代码审查标准.md` —— "查什么"：优先级化清单（🔴/🟡/💭）+ **§0 红线速查表** + 按模块专属红线（后端/前端/跨分支/测试）+ **反模式黑名单**（来自本项目踩坑史）。
   - `docs/代码审查流程.md` —— "怎么走"：角色职责、双分支工作流、触发条件、作者自检、CI 门禁联动、裁决三态、质量度量闭环。
   - `.github/PULL_REQUEST_TEMPLATE.md` —— 把自检清单与红线自查**固化进每次 PR 提交**。
2. **权威对齐**：审查标准的每一项红线都**显式引用 ADR/CLAUDE 条款**（如 ADR-017 判定语义单一真值源、ADR-015 零侵入、CLAUDE §前端三条硬约束）。通用最佳实践与 ADR 冲突时**以 ADR 为准**。
3. **CI 与人工互补**：CI 门禁（三套 workflow + 覆盖率 ≥50% + 建议的红线 grep 守护）为前置条件；但**CI 绿 ≠ 可合并**——红线违反、设计缺陷、口径漂移、合成兜底等必须靠人工审查拦截。审查结论是 CI 之外的第二道闸。
4. **角色轻量化**：作者自检 + 至少 1 名交叉审查者；把关人只审红线文件与跨分支影响，避免瓶颈。小团队（学术竞赛项目）现实下不强制双人 LGTM。
5. **持续改进**：每 PR 红线违反数、审查轮次、CI 红率由把关人季度回顾；反复出现的问题写回标准或升级为新 ADR。

## 影响

- **变容易**：审查者有可对照的权威清单，新人可快速上手；红线从"口头记忆"变为"可 grep/可引用"的文档；PR 模板强制自查降低漏检。
- **变困难 / 需注意**：
  - 标准需随 ADR 演进持续维护（新增红线/反模式须回流到标准 §2/§3），否则会腐化。
  - 红线 grep 守护（建议项）需谨慎设计豁免（如 `utils/api.ts` 的 fetch、worker CDN 拉取），避免误报疲劳导致团队绕过。
  - 多会话并发开发下，审查与合并仍需遵守"只 add 自己文件"（ADR-015 纪律 + 标准 §2.3④）。

## 备选方案（被否决）

- **仅靠 CLAUDE.md 口头约束**：红线分散、无优先级、无 PR 强制入口，已实际导致漏检，否决。
- **引入重型 CR 工具/强制双人 LGTM**：学术竞赛小团队成本高于收益、易卡流程，否决（采用轻量交叉审查）。
- **把红线全交给 CI 自动拦截**：部分红线（设计缺陷、口径漂移、合成兜底语义）无法靠静态检查捕获，否决（保留人工审查为必要闸）。

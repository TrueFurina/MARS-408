# SRE 可运维性 / 可靠性预备评估 — MARS-408 / study-help-pro

> **评估性质说明（重要）**：当前**无实时线上事故**。本次为**预备能力评估（preparedness assessment）**，对照 SRE 事故响应的「分诊 → 沟通 → 缓解 → 复盘」能力，评估系统在当前部署形态下的可运维性与可靠性，识别在真正事故来临时会拖慢响应、放大影响的结构性缺口。结论基于仓库真实文件证据，非推测。

评估对象：docker-compose.yml、Dockerfile、start*.bat/sh、stop*.bat/sh、recover.bat、py-server/（main.py、config.py、db/*、services/import_worker.py）、.github/（ci/test/secret-scan）。忽略 node_modules/、.venv/。

## 一、可运维性 / 可靠性评估

### 1. 部署流程
- **正向基线**：Dockerfile 多阶段构建（前端 node:22 → 后端 python:3.12-slim），创建非 root 用户 `netlearn` 并以 `USER netlearn` 运行；`restart: unless-stopped` 提供容器级自动重启（`docker-compose.yml:34,69,54`）；CI 有 `docker-build` 镜像可构建性门禁（`ci.yml:184`）。
- **致命缺口 — 生产 profile 未真正进入生产模式**：`docker-compose.yml` 的 `app` 服务 **未设置 `NETLEARN_ENV=production`**。`main.py:118-124` 与 `redis_client.py:17` 的 fail-fast / fail-closed 逻辑全部依赖该变量；缺失时容器以 `development` 模式运行 —— 自动播种 `demo/demo123456` 演示账户、生成**重启即失效**的随机管理员口令、限流保持 fail-open。`--profile production` 实际只额外拉起 Redis（`profiles:["production"]`），并未改变应用运行模式。
- **Milvus 与 production profile 分离**：`milvus` 服务的 `profiles:["milvus"]`（`docker-compose.yml:53`），而 `app` 的 `MILVUS_HOST=milvus`（`docker-compose.yml:20`）。执行 `docker-compose --profile production up -d` **不会**启动 Milvus → 应用连不上 → 静默回退 InMemoryVectorStore（`milvus_client.py:382-407`）。要真正用 Milvus 需 `--profile production --profile milvus`，文档/脚本未对齐。
- **无镜像版本 / tag 策略**：CI 构建为 `netlearn:ci`（`ci.yml:190`），无语义版本或不可变 tag，回滚目标不明确。
- **Windows 开发路径无编排**：`start.bat/start.sh` 手动拉起前后端到独立窗口，无容器化、无进程守护、后端崩溃无自动拉起。

### 2. 健康检查
- **端点可用**：`/api/status`（`main.py:269-283`）做真实依赖检查（向量库计数 + 配置读取），返回组件状态，优于纯存活探针。Dockerfile 与 compose 均有 healthcheck（30s/10s/3 retries）。
- **冷启动窗口与探针不匹配**：`backend_run.log` 实测冷启动 **~2.5 分钟**（21:16:52 → 21:19:22），主因 E5 模型加载 + 800 文档 embedding 在 lifespan 内同步执行。healthcheck 默认无 `start_period`，容器在镜像拉起后 90s 即可能因连续失败被标记为 unhealthy；编排层若按 health 摘除流量会误杀正在初始化的实例。**无 readiness/liveness 分离**。
- **Windows 脚本无就绪门禁**：`start.bat:43-51` 仅在固定 `ping -n 6` 延迟后做一次 httpx 探测，未就绪仅 WARN 并继续拉起前端 → 启动竞态。

### 3. 日志
- **正向**：`logging.basicConfig` 输出时间戳/logger名/级别（`main.py:46`），容器 stdout 可被 docker 采集；且**明确不打印明文口令**（`main.py:127-131` 仅记录「已生成」）。`.env`/`config.json`/`data/*.db` 均已 gitignore（`G4` 门禁通过）。
- **缺口**：无结构化（JSON）日志、无轮转、无集中聚合；Windows 控制台日志不落盘，事故后难复盘。

### 4. 端口管理（证据最硬）
- **实锤端口冲突**：`backend_run.log:33` 记录 `ERROR: [Errno 10048] ... bind ('127.0.0.1', 8002): winerror 10048` —— 真实发生的 Windows 僵尸 socket 占用。该次启动 lifespan 已完成（import worker 已起），但 uvicorn 绑定 8002 失败，进程随即 shutdown。
- **前端端口漂移 + CORS 失配**：`vite.config.ts:12-14` `port:5173, strictPort:false`；当 5173–5180 处于 TIME_WAIT，Vite 自增绑定到 **5181**。而 `recover.bat:17` 的释放循环只覆盖 **5173–5179（不含 5181）**，且 CORS 白名单仅含 `localhost:5173`（`main.py:211`）。后果：前端漂到 5181，用户访问 5173 失败、且即便通了也被 CORS 拒绝。
- **Windows TIME_WAIT 无 SO_REUSEADDR/SO_LINGER**：端口释放需重启机器，文档已承认此脆弱点。

### 5. Windows 特定问题
- 启动脚本用 `ping -n 6`/`timeout /t 8` 作 sleep hack（`start.bat:17,43`、`recover.bat:47`）；`taskkill /FI "WINDOWTITLE eq ..."` 按窗口标题字符串匹配，标题不符即漏杀（`start.bat:15-16`、`stop.bat:8-9`）。
- **pytest 段错误（SIGSEGV）**：Windows 原生库（pymilvus / torch 加载顺序、ChromaDB）触发，CI 因此全在 `ubuntu-latest` 跑且排除 `system`/`requires_milvus`（`ci.yml:160-163`）。代价：**Windows 本地开发者无法跑完整测试套件**，回归只能等 CI。
- **已缓解的残留风险**：`milvus_client.py:26-55` 通过 `find_spec` 探测 + 延迟 `import pymilvus` 规避「pymilvus 原生库早于 torch 加载触发段错误」，但副作用是 **Windows 上启用 Milvus 路径仍有 segfault 风险**，故开发期只能走 InMemoryVectorStore。
- `py-server/.venv` 实为指向 C: 的符号链接（`.gitignore:61` 注释：E: 空间不足），环境脆弱。

### 6. 故障恢复能力
- **正向**：`recover.bat` 提供杀孤儿进程 / 清 `__pycache__` / 干净重启的应急路径（仅 Windows）；Docker `restart: unless-stopped` 自动重启。
- **单写者硬约束限制扩展**：ADR-007 要求 `--workers 1`，`main.py:158-163` 在 `UVICORN_WORKERS>1` 时 `raise RuntimeError` fail-fast；`import_worker.py` 单消费者 + `store_lock` 串行化。结论：**禁止多进程/多副本**，横向扩容被架构封死，容量与高可用上限低。
- **无迁移框架**：PG schema 靠 `CREATE TABLE IF NOT EXISTS` 在 connect 时隐式创建（`pg_client.py:95-135`），无迁移工具/版本化 → schema 漂移风险、无 schema 回滚。
- 仅 docker-compose 编排，无 k8s、无 Windows 进程管理器（systemd/supervisor）。

### 7. 配置 / 安全
- **正向**：密钥经环境变量注入，`ADMIN_PASSWORD`/`AUTH_SECRET` 在 compose 中**无默认值**（fail-fast，`ci.yml:33-40`）；gitleaks + G1–G12 安全门禁固化。
- **实锤**：`backend_run.log:1,28` 显示 `AUTH_SECRET` 与 `ADMIN_PASSWORD` **运行期未注入** → 生成临时随机密钥（**重启后所有已签发 JWT 失效**），管理员口令重启即丢。必须由部署环境注入。

## 四、给事故响应流程的预备建议（若真有事故）

1. **分诊提速**：上线 `/metrics` + 外部探针，避免冷启动期误判 unhealthy。
2. **沟通模板**：内部状态更新 / 客户通知草稿应预置（目前仅有 `recover.bat` 应急脚本，缺状态广播机制）。
3. **缓解手册**：把 D3 端口漂移、D1 密钥注入写成 runbook（含 `netsh` 释放 TIME_WAIT、env 注入清单）。
4. **复盘机制**：当前 `deliverables/` 已有历史 incident 文档，建议沉淀为无责复盘模板。

# 芒得很职 · MARS-408 职业素养对抗实训改造方案（代码级·可执行）

> 项目全称：芒得很职——新一代多智能体赋能的计算机类学生职业素养对抗实训平台
> 技术底座：MARS-408（Vue3 + FastAPI + LangGraph）
> 分支：`career-literacy`（已从 main 创建）；main 保留 408 考研系统用于国家级大创结题
> 文档版本：v1.0 · 2026-09-11 · 基于对仓库源码的逐文件核查，非想象稿

---

## 0. 结论先行（30 秒看懂）

1. **现有 MARS-408 是一条"一次性学习资源生成流水线"**：输入一个 408 知识点 → 10 节点流水线 → 一次性产出 7 种学习资料（讲解/题库/思维导图/拓展/代码/PPT/视频脚本），其中 Critic 是"对生成资料做事实核查"，**不是多轮对话对抗**。
2. **芒得很职要的是"多轮对话对抗循环"**：画像 → 生成情景脚本 → 学生与 AI 面试官多轮交锋（每轮留证）→ 对话结束后按证据做 6 维软素养评分 → 输出可溯源报告。这是**交互范式的改变**，不是改几个 prompt 能完成的。
3. **但底座 70% 可复用**：LLMProvider、FrugalRAG 检索、evidence_check（证据核查，最成熟的 19KB 节点）、quality_gate（质量闸门）、三层记忆、pg/redis/milvus、前端框架与 ECharts 全部保留。
4. **总策略 = 双图并存，不在原图上硬改**：新建 `career_graph.py`（对抗实训图）与现有 `graph.py`（408 生成图）并列，通过 API 路由区分；main 分支的大创代码零破坏。
5. **真正的新代码核心只有 4 块**：①多轮对话的 interrupt-resume 人机协同机制；②对抗 Agent（含鲶鱼加压）；③对话证据结构化采集；④6 维 ECD 评估。其余是改造和数据填充。
6. **工期：12 周可做出竞赛可演示 + 46 人试点可跑的完整闭环。**

## 1. 现状诊断：MARS-408 真实代码盘点

### 1.1 现有 10 节点流水线（`py-server/agents/graph.py` 实测）

```
coordinator → diagnostician → planner → retriever
   →（有检索结果?）→ generator_cluster → assessor → critic
   →（critic判定）→ evidence_check → quality_gate
   →（PASS）→ path_planner → END
   →（FIX） → generator_cluster 重生成（最多 max_regenerate_rounds，默认1）
   →（REJECT/耗尽）→ 降级通过或 END
```

| 节点 | 文件 | 实测职责 | 与芒得很职的关系 |
|---|---|---|---|
| coordinator | coordinator.py (4KB) | 全局协调、参数归一 | **改造**：改为"实训场景路由" |
| diagnostician | diagnostician.py (6.5KB) | 408 学情诊断、薄弱章节 | **改造**：改为 6 维软素养画像 |
| planner | planner.py (3.5KB) | 拆解 7 种资源生成任务 | **改造**：改为对抗情景脚本规划 |

| assessor | assessor.py (7.9KB) | 评估"生成资源质量"（准确性/难度匹配…） | **重写**：改为评估"学生 6 维素养" |

### 1.3 关键判断

> 现有系统的"多智能体"是**并行生成 + 串行质检**的流水线智能体；芒得很职的"多智能体"是**角色化编排 + 人机多轮 + 证据评估**的交互式智能体。骨架（检索/证据/闸门/记忆/LLM/前端）可继承，"生成集群 + 单次 Critic"这一段必须换成"对抗循环 + 证据评估"。

## 2. 根本差异：从"资源生成"到"对话对抗循环"

### 2.1 两种范式对比

| 维度 | 现有 408 流水线 | 目标对抗实训 |
|---|---|---|
| 触发方式 | 一次 invoke 跑到 END | 多轮：每轮等学生输入后 resume |
| 核心产物 | 7 种学习资料 | 一份带证据溯源的 6 维评估报告 |
| Critic 角色 | 审"资料对不对"（机器对机器） | 演"面试官/评审"（机器对人，多轮） |
| 过程数据 | 中间文本 | **每一轮问答 = 一条评估证据** |
| 评估对象 | 资源质量 | 学生表现（表达/抗压/拆解/协作/汇报/解决） |
| 终止条件 | 质量闸门通过 | 达到设定轮数 / 学生主动结束 / 触发收敛 |
| 时间尺度 | 数十秒一次性 | 8–15 分钟、6–10 轮交互 |

### 2.2 核心技术挑战：图不能"阻塞等学生输入"

LangGraph 一次 `invoke` 是一次完整执行，**不能在节点里挂起等前端传下一句话**。正确做法是 LangGraph 的**人机协同（human-in-the-loop）中断-恢复**：

- 图运行到"对抗 Agent 生成下一问"后调用 `interrupt()` 把问题抛给外层、保存检查点（checkpointer），图暂停；
- 前端拿到问题展示给学生，学生回答后，带着 `thread_id` 和学生答案调用 `graph.invoke(Command(resume=学生回答), config)`；
- 图从断点恢复，把学生答案写入证据、判断是否继续，再生成下一问或进入评估段。

> 这是整个改造在技术上唯一"新"的硬骨头，其余都是业务逻辑。第 11 节给出落地方案与"不用 checkpointer 的简化备选"。

## 4. 新对抗实训图设计（career_graph）

### 4.1 业务"四角色 + 鲶鱼" ↔ 技术节点映射（修正计划书口径，以代码为准）

| 业务角色 | 技术实现节点 | 来源 |
|---|---|---|
| ① 画像 Agent | `career_coordinator` + `career_diagnostician` | 由 coordinator/diagnostician 改造 |
| ② 脚本 Agent | `scenario_planner`（规划）+ retriever（检索情景库）| planner 改造 + retriever 复用 |
| ③ 对抗 Agent（含**鲶鱼**） | `adversary`（多轮循环，动态加压） | **新建**，由 critic 彻底重写 |
| ④ 评估 Agent | `evidence_collector` + `career_assessor` + evidence_check + quality_gate | 新建 + assessor 重写 + 两个质检节点复用 |

### 4.3 多轮对话 interrupt-resume 机制（关键）

**状态里新增对话控制字段**（见 5.2 career_state）：`dialogue_turns[]`、`current_turn`、`max_turns`、`adversary_mode`（normal/escalating/catfish）、`scenario_script`、`dimension_focus`。

**adversary 节点伪代码**：

```python
async def adversary_node(state):
    history = state["dialogue_turns"]
    script = state["scenario_script"]
    # 1) 鲶鱼判定：若近2轮评分标记"过于顺畅/答案模板化/维度无差异"→ 切换加压模式
    mode = decide_adversary_mode(history, state["adversary_mode"])
    # 2) 结合情景脚本、历史对话、当前要考察的薄弱维度，生成下一问（强制JSON）
    next_q = await llm.text_completion(ADVERSARY_PROMPT[mode], build_ctx(...))
    # next_q = {question, probe_dimension, intent, expected_signal, difficulty_delta}
    # 3) 未达终止条件 → interrupt，把问题交给学生；图在此暂停并落检查点
    if not should_terminate(history, state):
        payload = interrupt({"next_question": next_q, "turn": len(history)+1})
        # resume 后 payload 即学生本轮回答
        state["_student_answer"] = payload
    return state
```

**API 侧驱动**（`api/career_training.py`）：

```python
@router.post("/session/{sid}/answer")
async def answer(sid, body):
    config = {"configurable": {"thread_id": sid}}   # 每会话一线程，checkpointer记忆断点
    result = await career_graph.ainvoke(
        Command(resume=body.answer), config=config)
    # 若结果里含 interrupt 载荷 → 返回下一问（继续对话）
    # 若已到 END → 返回评估报告
    return derive_response(result)
```

**简化备选（若 checkpointer 调试成本过高，竞赛 Demo 可先用）**：不在图内 interrupt，改为"API 层持有对话状态、adversary 作为无状态函数逐轮调用"，即把循环放在 API/前端，图只负责"启动准备"和"收尾评估"两段。代价是架构图没那么"自动化"，但**开发快、稳定、好演示**；论文与答辩仍可描述为 LangGraph 角色编排。建议：**先用简化备选跑通全链路（阶段2），再升级为真 interrupt（阶段4加分项）。**

### 4.4 鲶鱼 Agent 唤醒逻辑（对应前沿 Catfish，防"群体/自我附和"）

对抗是机器对人，鲶鱼在这里的作用是**防止学生用背模板的方式"平顺过关"**：
- 触发信号（满足≥2）：连续 2 轮被 evidence_collector 标记 `template_suspect=true`；6 维中某维一直无有效证据；答案长度充足但信息密度低；学生主动表达"我准备好了/没问题"等过度自信信号。
- 加压动作：切换 `ADVERSARY_CATFISH_PROMPT`，进行反事实追问（"如果线上故障发生在你答辩前一小时，且你无法联系到导师？"）、要求给出具体数字/取舍、故意质疑其方案前提。
- 退出：学生给出一次高质量具体回应，或加压满 2 轮即回到 normal（避免一直高压影响体验）。
- 全程在报告里标注"鲶鱼加压轮"，作为抗压应变维度的关键证据。

### 5.2 `career_state.py` 字段表（新建，不动旧 state.py）

```python
class CareerState(TypedDict):
    # —— 输入 ——
    user_id: str
    task_id: Optional[str]          # 教师布置的实训任务（学生自主练习时为空）
    scenario_type: str              # defense/review/incident/conflict（4类）
    scenario_subtype: str           # 12子场景之一
    difficulty: str                 # easy/medium/hard
    max_turns: int                  # 默认 8
    # —— 画像 ——
    initial_profile: dict           # 6维先验 {expression,stress,decompose,collab,presentation,problem_solving}
    # —— 脚本 ——
    scenario_script: dict           # 背景/角色/追问树/考察维度/rubric
    retrieved_refs: list            # 情景范例与评分标杆（retriever）
    # —— 多轮对抗（核心）——
    dialogue_turns: list[dict]      # 每轮 {turn_id, question, answer, evidence, mode, ts}
    current_turn: int
    adversary_mode: str             # normal/escalating/catfish
    catfish_triggered: bool

    evidence_report: Optional[dict] # evidence_check 写入（与旧图同名，便于复用节点）
    gate_verdict: str
    gate_reasons: list
    # —— 路径 ——
    improvement_plan: dict
    # —— 控制 ——
    status: str
    error: Optional[str]
```

## 6. 数据库设计（5 张新表，均 `career_` 前缀，pg/sqlite 双写）

```sql
-- 1. 班级（教师创建，46人试点用）
CREATE TABLE IF NOT EXISTS career_classes (
    id VARCHAR(64) PRIMARY KEY,
    teacher_id VARCHAR(64) NOT NULL,
    class_name VARCHAR(128) NOT NULL,     -- 如 信息安全1班
    student_count INTEGER DEFAULT 0,
    created_at TIMESTAMP DEFAULT NOW()
);
-- 2. 实训任务（教师发布：选场景/难度/截止时间）
CREATE TABLE IF NOT EXISTS career_tasks (
    id VARCHAR(64) PRIMARY KEY,
    class_id VARCHAR(64) REFERENCES career_classes(id),
    teacher_id VARCHAR(64) NOT NULL,
    scenario_type VARCHAR(32), scenario_subtype VARCHAR(64),
    difficulty VARCHAR(16), max_turns INTEGER,
    due_at TIMESTAMP, created_at TIMESTAMP DEFAULT NOW()
);
-- 3. 实训会话（一个学生一次完整对抗）
CREATE TABLE IF NOT EXISTS career_sessions (
    id VARCHAR(64) PRIMARY KEY,
    user_id VARCHAR(64) NOT NULL,
    task_id VARCHAR(64),                  -- 自主练习可空
    scenario_type VARCHAR(32), scenario_subtype VARCHAR(64),
    status VARCHAR(16),                   -- ongoing/finished/abandoned
    turn_count INTEGER DEFAULT 0,
    started_at TIMESTAMP DEFAULT NOW(), finished_at TIMESTAMP
);
-- 4. 对话轮次（每轮=一条证据单元，ECD过程性数据核心）
CREATE TABLE IF NOT EXISTS career_dialogue_turns (
    id SERIAL PRIMARY KEY,
    session_id VARCHAR(64) NOT NULL,
    turn_index INTEGER NOT NULL,
    adversary_mode VARCHAR(16),           -- normal/escalating/catfish
    question TEXT, answer TEXT,
    evidence JSONB,                       -- 维度命中/行为标记/原话摘录/模板检测
    probe_dimension VARCHAR(32),
    ts TIMESTAMP DEFAULT NOW()
);
-- 5. 评估报告（6维分+证据绑定+提升路径）
CREATE TABLE IF NOT EXISTS career_assessments (
    id VARCHAR(64) PRIMARY KEY,
    session_id VARCHAR(64) NOT NULL,
    user_id VARCHAR(64) NOT NULL, task_id VARCHAR(64),
    dimension_scores JSONB,               -- 6维分+置信度
    evidence_chain JSONB,                 -- 分→turn_id绑定
    consistency_score FLOAT,              -- evidence_check 一致性
    improvement_plan JSONB,
    report_md TEXT,
    created_at TIMESTAMP DEFAULT NOW()
);
```

> SQLite 回退：`JSONB→TEXT`、`SERIAL→INTEGER PRIMARY KEY AUTOINCREMENT`、`TIMESTAMP→TEXT`，照现有双写范式。

## 11. 关键技术难点与解法

1. **图如何等学生输入** → 首选 LangGraph checkpointer + `interrupt()`/`Command(resume=)`（MemorySaver 开发期、PostgresSaver 生产期，thread_id=session_id）；**竞赛先用 4.3 的"API 持有状态、adversary 无状态逐轮调"简化备选**，跑通后再升级，避免一上来被框架卡住。
2. **评分必须可信、不能 LLM 随口给分** → 强制 JSON、BARS 行为锚定、**每分挂 turn_id**；evidence_check 复核"分-证一致性"；无证据维度标 `insufficient` 并在 quality_gate 拦截，禁止编分（沿用现有 fail-open/规则降级且诚实标注的风格）。
3. **防学生背模板/刷分** → evidence_collector 做模板/套话检测 + 鲶鱼加压；过程性证据（多轮）比最终答案更重要，这正是 ECD 与计划书核心卖点。
4. **多轮 LLM 调用成本与时延** → 对应 A-HMAD/Council 的"分诊"思想：画像/取证用轻量参数、只在评估段用强模型；单轮只传"脚本+近3轮+维度摘要"，不全量堆历史；max_turns 默认 8 封顶。
5. **LLM 输出不稳定** → 全部 JSON schema 约束 + 解析降级（学现有 critic `_parse_*` 的 JSON 优先、关键词兜底）；任何异常 fail-open 但在报告标注"规则降级"。
6. **408 与职业两套不串味** → 表 `career_*`、API `/career`、前端 `/career`、独立 `career_graph`；公共文件只增量注册；main 分支永不混入职业代码。
7. **名单与隐私** → 导入仅留学号后 4 位 + 姓名，对话内容按 user_id 隔离，符合计划书合规表述。

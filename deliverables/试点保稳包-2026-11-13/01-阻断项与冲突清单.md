## P0-3 `scripts/deploy-oneclick.ps1` 五个缺陷（只读走查，未修改）

脚本 11-13 刚提交（`74e1280`），注释 L9-11 声称「任一步失败自动回滚并重启」，但实现并非如此。以下按对 11-18 的风险排序：

| # | 缺陷 | 定位 | 影响 |
|---|---|---|---|
| 1 | **回滚只包住「重启并探活」** | `try { Restart-Backend } catch { …回滚… }` 在 L169-185；而上传校验 L116、`py_compile` L118、备份 L123、落位校验 L128、dist 文件数校验 L151 全部在 try 之外 | 最常见的一类失败（上传 sha 不符、编译失败、dist 解压数不符）会**直接 throw 退出，不回滚、不重启**，线上停在「部分文件已覆盖」的半部署状态。与注释严重不符 |
| 2 | **健康检查判定过弱** | `Wait-Healthy` L58-66 只判 `status -eq "ok"`；`Restart-Backend` L68-73 复用它 | 不检查 `degraded_reasons` / `health.llm.available` / `health.embedding.loaded`。11-12 真实发生过「DeepSeek key 欠费 → 静默降级为规则兜底」，此时 `status` 仍可能是 ok，脚本会打印「完成」——**恰好漏掉最会毁课的那类故障**。反倒是 `-HealthOnly` L83-85 会打印这三个字段 |
| 3 | **`-DryRun` 不纯** | L144 只跳过 dist 上传；L162 `-NoRestart` 单独判断；L167 起照常重启 | `-Frontend -DryRun` 会**真实重启生产服务**。预演时若忘了加 `-NoRestart` 就会误触 |
| 4 | 备份不清理 | `$bak.$Stamp` L122/L153，无清理逻辑 | 每次部署累积两份 dist 全量备份，长期吃磁盘；且回滚后旧备份仍在，需人工辨认时间戳 |
| 5 | 编译校验有限 | L118 编译的是 `$stage/$rel`，不是目标模块 | 只验语法，不验导入（例如新增依赖缺失、循环导入），重启后才炸 |

**本轮已落地的补丁（工作区改动，未提交）**
1. 新增 `Invoke-Rollback -Backups -Reason` 函数统一回滚逻辑；把后端文件段与前端 dist 段整体包进 `try { … } catch { 清理 stage → Invoke-Rollback → throw }`，让「任一步失败自动回滚」名副其实；重启段的 catch 改为复用同一函数（不再有第二份副本）。
2. `Restart-Backend` 新增严格健康门禁：除 `status=="ok"` 外校验 `degraded_reasons` 为空、`llm.available=True`、`embedding.loaded=True`，不满足即抛错并提示「多为 LLM 通道/配置问题，回滚代码不修 key」；新增 `-SkipHealthGate` 作为紧急逃生开关。收尾统一打印 status / degraded / llm / embedding / 向量库条数。
3. `-DryRun` 在部署动作之后直接 `exit 0`，**不再触发真实重启**（原手册 A1 要求「务必带 -NoRestart」，现已不必要）。
4. 收尾打印本次 `.bak.$Stamp` 清单供人工确认后清理，**脚本不自动 rm**。
5. 缺陷 5（只编译 stage 文件、不验目标模块导入）**保留未改**：改动涉及远端编译路径与导入语义，收益有限而风险不低，留到试点后评估。

> 校验：PowerShell `[Parser]::ParseFile` 静态解析 0 错误；文件 BOM 仍为 `EF BB BF`（Windows PowerShell 5.1 读中文注释不会乱码）；未执行脚本、未连远端。预演方法见 `02-试点前预演与演练手册.md` A 节（A1/A4 已同步更新）。

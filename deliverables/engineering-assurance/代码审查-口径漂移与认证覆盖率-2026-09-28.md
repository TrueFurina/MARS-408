## 三、就绪修的一条隐患：密钥门禁把接口快照永久冻结

同步 `openapi.json` 时被 pre-commit 密钥扫描拦下 13 处，经逐行核对**全部是误报**：

```
❌ py-server\openapi.json:9663: 疑似密钥 - /components/schemas/ResourceRecommendReq
```

根因：低精度规则 `[0-9a-zA-Z/+]{40}`（AWS Secret Access Key 形态）匹配**任意 40 字符以上
字母数字串**，而 `"$ref": "#/components/schemas/<长名字>"` 中
`/components/schemas/XXX` 本身就是一个 40+ 字符串（`/` 属于该字符类）。
与 `scripts/pre-commit/secrets_scan.py` 中已记录的 `py-server/seed/` 误报**同源**。

后果不止噪点：pre-commit 只扫描**暂存文件**，因此该快照一旦被拦，
**此后任何一次更新都提交不进去**——事实上已被冻结。

修复（`62ba92f`）：沿用文件内既有先例，只对**这一条低精度规则**、**这一个文件**豁免；
generic / 连接串 / JWT / 私钥四类规则对它依然生效。

**变异验证**：向同路径文件注入假 JWT + 假 GitHub Token + 假 AWS Key ID，三条**全部仍被抓到**，
确认豁免范围精确、未弄瞎其余规则。

## 四、待裁决（本轮只报不改）

### 🔴 D-1. 职业素养测评三个端点无鉴权

`py-server/api/literacy_assessment.py`（对照实验载体，零 `Depends`）：

| 端点 | 风险 |
| --- | --- |
| `GET /api/literacy/report/{user_id}` | `user_id` 即「学号后 4 位」，仅需 10⁴ 次枚举 → **未登录读取任意学生六维测评报告（IDOR）** |
| `POST /api/literacy/class-report` | 输入班级名即返回 **全班学生 `user_id` + `user_name` + 逐人六维明细** → 批量个人信息泄露 |
| `POST /api/literacy/submit` | 请求体 `user_id` **优先于 token**（代码注释说明：全班共用 demo 账号会互相覆盖，故刻意如此）→ 未登录即可**以任意学生身份写入/覆盖**其前后测记录 |

**为什么这项特别重**：该模块是教改/国创赛对照实验的**原始数据入口**。
上述三条合起来意味着——研究的关键原始数据，第三方既能**读**（含姓名）也能**改**。
若数据可信性被质疑，影响的不是接口，是研究结论本身。

**为什么没有直接改**：加鉴权会与「全班共用 demo 账号」的课堂流程冲突
（学生端 `LiteracyAssessmentView.vue` 目前硬编码调用 `/literacy/report/demo`，
不带 token 即 401）。这是流程设计权衡，且属职业代码线，按分工不擅自改动。

**可选方案**：

- **方案 A（推荐，改动最小）**：给两个**读**接口（`report`、`class-report`）挂
  `Depends(require_teacher_or_demo_open)`。该依赖已存在且正是为这种场景写的：
  生产环境仅放行 admin/teacher；演示环境设 `NETLEARN_DEMO_TEACHER_OPEN=1` 即可放行 demo 账号，
  且每次放宽都写 `[DEMO-RELAX]` 审计日志（**永不静默**）。
  `submit` 保持公开（学生答题必须能提交），风险以「实验数据可被覆盖」单独记录。
- **方案 B（不改鉴权，改数据形状）**：`class-report` 只返回聚合均值、不回姓名与逐人明细；
  `report/{user_id}` 改为凭据换取的短时链接。改动面更大，但不动课堂登录流程。
- **方案 C（接受现状）**：明确写下「课堂演示环境，数据非真实学生」的前提，
  并把该前提写进对外说明——前提不成立时风险立即回归。

### 🟡 D-2. 对外数字 97.8% 的处置

实测 93.4% 与宣称 97.8% 不符。三个选项：

- **A**：把对外数字统一改为**实测值**并用脚本产出（数字有源可复现）；
- **B**：改为**不带数字**的表述（如「除登录/注册外全部需鉴权」），回避快照式数字再度失效；
- **C**：补齐鉴权后重算，再对外宣称——需先完成 D-1。

> 提醒：97.8% 还出现在**演示视频字幕**（`deliverables/.../作品录屏.srt`）等**已固化的交付物**里，
> 改代码侧文案不会让它们同步。若选择 A/B，需一并决定这些固化物如何处理。

### 🟡 D-3. 接口快照与前端类型的同步链

`py-server/openapi.json` 是入库快照，实测为当前路由的**严格子集**：223 vs 227，
**仅缺 4 个 `/api/cn-distinction` 路径**。完整同步是两步机械操作：

```bash
# 1) 从运行中的服务重生成快照（或由 app.openapi() 导出）
# 2) 再由快照生成前端类型
npm run types:generate        # openapi-typescript py-server/openapi.json -o src/types/api.generated.ts
```

未擅自执行的原因：第 2 步会改动 `src/types/api.generated.ts`（2900+ 行生成物），
属前端线，需要你确认联调窗口。

- `GET /api/experiments` 响应中回传 `results_dir`（服务器绝对路径）。属轻微信息泄露，
  是否保留取决于是否把它当作「证据可追溯」的一部分。
- `app/errors.py` 在 `NETLEARN_ENV=production` 时把错误体从 `{"detail": ...}` 换成
  `{"error": {"code", "message"}}`。前端已同时兼容两种形态
  （`src/utils/api.ts`：`body?.detail || body?.error?.message || ...`），**这一处做对了**。
  唯一缺口是上传路径 `src/utils/api.ts:300` 只取 `data?.detail`，
  生产模式下上传失败会退化成通用文案「上传失败 (status)」——排查成本不高但值得顺手对齐。
- `main.py` 描述中的「13 个智能体」「7 种学习资源并行生成」**本轮未核**
  （本轮机验只覆盖节点数）。已确认的事实是：**代码里不存在"智能体花名册"**——
  `agents/__init__.py` 只导出 `AgentState / agent_graph / create_agent_graph`，
  不枚举任何 agent，故「13」目前是一个**无源码锚点的宣称**，无法用同款断言锁死。
  11 节点与 13 智能体并不矛盾（`generator_cluster` 一个节点承载多个生成智能体），
  但要坐实它，需要先在某处建立权威清单（例如图节点 + 集群内角色表），建议纳入下一轮口径核查。

## 二、🔴 机验假红灯：完整归因

### 现象
```
[FAIL] 每一步的返回值/错误与基线完全一致
       ['get_or_create_daily_plan', 'get_platform_stats', 'list_daily_plans']
RESULT: HAS FAILURE      exit=1
```

### 逐键差分（`TOTAL DIFF STEPS: 3`）
| 步骤 | 基线（09-27 采） | 当天（09-28） |
|---|---|---|
| `get_or_create_daily_plan.plan_date` | `"2026-09-27"` | `"2026-09-28"` |
| `list_daily_plans[0].plan_date` | `"2026-09-27"` | `"2026-09-28"` |
| `get_platform_stats.daily_quiz` | `[09-21 … 09-27]` | `[09-22 … 09-28]`（近 7 日窗口整体平移一天，count 分布一致） |

**结论：零行为语义差异。** 拆分没有回归。这纯粹是"今天是几号"造成的黄金快照漂移。

### 根因链（两层）
1. **探针用真实时钟**：`_clean()` 归一了动态时间戳（`created_at` 等）与随机 uid（`u_<16hex>`），但**没归一"当天日期"**——`plan_date` 是 `%Y-%m-%d`，`daily_quiz` 是滚动 7 日窗口。
2. **生产代码有一处函数内重导入**（`db/user_store.py:1049` `from datetime import datetime`），它**遮蔽了模块顶部的 `datetime`**，使任何模块级打桩/冻结时钟对它无效。我第一次只冻结了时钟，另外两步立刻归位，唯独 `plan_date` 纹丝不动——正因如此才把它揪出来。

### 修复
- `scripts/user_store_behavior_probe.py`：新增 `_FrozenDatetime`（把"今天"钉在基线的 `2026-09-27 10:00`），在**任何写入之前**替换 `db.user_store.datetime` 与 `db.profile_store.datetime`。只改探针，**不在生产代码里加任何测试开关**。
- `db/user_store.py`：移除 `get_or_create_daily_plan` 内的 `from datetime import datetime`（与文件其余部分的顶层导入保持一致，语义完全不变），并就地注释记录为何此处不许再写局部导入。

### 验证（全部机验，非口头）
```
verify_app_wiring              PASS(exit0)
verify_core_lock_unification   PASS(exit0)
verify_seed_data_split         PASS(exit0)
verify_user_store_split        PASS(exit0)      ← 由 FAIL 转 PASS

探针 42 步 vs 拆分前冻结基线： TOTAL DIFF STEPS: 0
```
**变异验证**（证明门禁没被治瞎）：把 `strftime("%Y-%m-%d")` 改成 `"%Y/%m/%d"` →
```
[FAIL] 每一步的返回值/错误与基线完全一致 ['get_or_create_daily_plan','list_daily_plans']
RESULT: HAS FAILURE
```
→ 已还原，`grep '%Y/%m/%d'` 无残留，机验回到 ALL PASS。

## 三、🟡 建议（都涉及行为变化，未动手）

### S1 ｜ 生产环境管理员初始化失败应 fail-closed
`app/lifespan.py:130-137`：
```python
try:
    ensure_admin(...)
except Exception as e:
    logger.warning(f"管理员账号初始化失败: {e}")   # ← 仅告警，应用照常起来
```
**问题**：同一文件里 `AUTH_SECRET`、`ADMIN_PASSWORD` 缺失/过短都是**直接 raise**（fail-closed），唯独"管理员账号最终没建成"只打一条 warning。结果是**可以带着零管理员的生产实例上线**——口令再强也没人能用。**不一致的守门口径最容易被误判为"反正都是 fail-closed"**。
**建议**：`production` 下改为 `raise`，其余环境保持降级。

### S2 ｜ 单写者守卫执行得太晚
`app/lifespan.py:290-297`：当前顺序是 **PG/Redis/Admin → migrations → demo seed → LLM 检查 → `_assert_single_worker()`**。
**问题**：`--workers 4` 时每个 worker 都会先跑完迁移、写演示账户，最后才被告知"你不该起来"。ADR-007 想防的是多写者竞态，而这恰恰是在**已经多写者写入之后**才拦。
**建议**：把 `_assert_single_worker()` 提到 lifespan 最前面（在任何写库动作之前，成本几乎为零）。注意文件头明确写了"顺序是有意为之"，故仅建议、未改。

### S3 ｜ 限流器无条件信任 `X-Forwarded-For`
`app/middleware.py:96-104`：`_client_ip()` 只要请求带 `X-Forwarded-For` 就采信第一个值。
**问题**：在**没有前置可信反代**的部署下，客户端自己就能随手伪造这个头 → 每换一个值就是一个新的限流桶 → **限流器可被完全绕过**。当前单进程、无公网暴露时不可利用；一旦挂到 nginx/网关后面这个头就变成攻击面，但它不校验来源。
**建议**：加 `TRUSTED_PROXY_IPS` 白名单，仅当 `request.client.host` 在其中时才采信 XFF/X-Real-IP；否则只用 socket IP。

### S4 ｜ 限流桶会缓慢泄漏内存
`app/middleware.py:88-99`：`_rate_buckets` 按 `(ip, group)` 存 deque，过期时间戳**只在同一个 key 再次被访问时才清理**。
**问题**：大量不同来源 IP（或伪造 IP，见 S3）各留一个 key，永不回收。属缓慢增长型泄漏。
**建议**：加一个轻量定期清扫（例如每 N 次请求或起一个后台 tasks 扫描并删除空/过期桶），或对字典规模设上限。

### 💭 小项（可不改）
- `X-XSS-Protection: 1; mode=block` 已被主流浏览器移除，保留无害但会被安全扫描器标黄。
- CSP 生产策略建议补 `base-uri 'self'; form-action 'self'; object-src 'none'`（当前靠 `default-src 'self'` 兜底，显式更稳）。
- `/showcase` 在生产刻意降级到开发版 CSP（为了展示页的内联脚本）——这是有理由的例外，已在代码注释说明，**请勿当作 bug "顺手修掉"**。
- `logger.warning(f"...")` 与文件中其余 `%s` 惰性格式化风格不一致（每次都会先拼字符串），统一即可。

## 四、做得对的地方（值得保留的模式）
- **启动顺序写成显式文档 + 注释理由**（`lifespan.py` 文件头），重排序前必须先回答"为什么是这个顺序"——这是拆分最容易丢的信息，这里保住了。
- **口令从不落日志**：随机生成管理员口令只记录"已生成"，演示Seed以 `DEMO_USERNAME/DEMO_PASSWORD` 为唯一真值源，杜绝了"改了口令却漏改幂等探测"的漂移。
- **CORS 单一真值源 + 测试锚点**：`middleware.py` 头部直接写明"安全测试的静态复查以本文件为准"，审查者不会找不到真相。
- **黄金探针用"行为差分"而不是"对象 repr 差分"**（函数含内存地址，repr 必然变）——这个选择在本次排查中证明了价值：它让我能一眼看出差异只是日期。

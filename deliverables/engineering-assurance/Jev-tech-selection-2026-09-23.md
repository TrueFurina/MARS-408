# Jev 技术选型评估（TypeSafe AI · System One 决策模型）

> **项目**：study-help-pro（分支 `career-literacy`，对外产品名「芒得很职」）
> **评估对象**：TypeSafe AI Jev（System One 模型）
> **报告日期**：2026-09-23
> **事实源**：Jev 发布信息（2026-09-15）；我方实测现行口径 `py-server/experiments/results/benchmark_2026-09-18.json`
> **产出**：产品经理 许清楚（研究模式）｜交付总监 齐活林 汇编
> **执行边界**：本报告为**只读调研**——未修改任何代码、未接入运行链路、未调用任何外部 API。所有结论在本阶段**不落代码**。

---

## 1. TL;DR 与结论

**结论：有条件建议接入——只在旁路试点，不替代、不改主线。**

不建议现在把 Jev 接进 11 节点主线。建议以最低优先级做一次「零改主线」的旁路对照实验，仅覆盖 triage / critic / evidence_check / assessor 四个**判断型**节点；前置条件是拿到 API key、用户授权、全程只读旁路。

必须同时纠正一个**类别错误**：Jev 与 FrugalRAG 不构成替代关系。FrugalRAG 是检索组件（本地 E5-base-v2 768 维向量 + BM25 融合 + 课程软过滤 + 余弦阈值），Jev 不做检索。用 Jev 替换 FrugalRAG 等于取消检索层，不是优化。

---

## 2. 问题定义：把「省 token」纠正为真实问题

原始诉求是「Jev 很快又省 token，能否替代/补充当初为了省而选的 FrugalRAG」。这个前提本身不成立：

- 现行口径下 FrugalRAG 的 token/查询 **185.75**，全量检索 **165.86**，**反而高出 11.99%**；延迟 **574.36 ms vs 2.70 ms**，约 **213 倍**更慢。它当前的实测收益**不在成本侧**。
- 它的收益在质量侧：Recall@5 **+7.14 pp**、Precision@5 **+15.71 pp**、MRR **+12.38 pp**。
- 旧口径曾记 token −0.14%，与现行口径不一致；内部审计 `deliverables/engineering-assurance/metrics-integrity-audit-2026-08-29.md` 已把申报书「检索成本降低 45%」列为 🔴 禁止使用，`documents/大创真版证据链_2026-08-20.md` 明文「不应宣称降本/提速」。

**真实问题陈述**：不是「谁更省」，而是「问答的成本与质量分别卡在哪一段，能否用更便宜的组件在同一段上取得同等或更好效果」。从架构看，token 大头在**生成型调用**（generator_cluster 与生成链路），检索层只占小头。因此拿一个「不能生成文本」的模型去替检索层，既降不了生成成本，又砍掉质量来源。

一句话：**要优化的是生成侧成本与判断侧延迟，Jev 的可用位置在这个窄缝里。**

## 3. 能力边界

**Jev 是什么**：TypeSafe AI 于 2026-09-15 发布的非自回归「System One / 决策模型」，创始人 Diogo Almeida（前 OpenAI，RLHF 共同发明人），$40M 种子轮。输入一段文本 state，输出**类型化判断**，三原语：

| 原语 | 语义 | 输出形态 |
|---|---|---|
| **Choice** | 从 ≤255 个选项中选一个 | 选项 + 概率分布 |
| **Score** | 按有序量程打分 | 量程内浮点分 |
| **Noul** | 是/否命题 | 0–1 概率 |

同一请求内多个问题**并行**求值。定价 **$0.042 / 百万输入 token，输出免费**（没有输出 token 可计费）；官方称延迟 70–500 ms；官方自评 4-workflow benchmark ≈ **67.8%**；一个独立 108-claim 测试报 **96.3%**（两者口径不可直接比较）；校准 ECE **0.07**（优于基线 0.14–0.18）。可用性：**仅托管 API**（`api.typesafe.ai/v1/systemone`），早期访问，**不公开权重、无可自托管方案**，提供 Python / JS SDK。命名来自 Jevons 悖论。

**Jev 不是什么（硬边界）**：

- **不是 RAG**：不做检索，无索引、无召回
- **不是 LLM**：不生成任何文本
- **不是可自托管组件**：与「离线可复现」基座天然冲突

一句话：**能判断，不能检索，不能生成文本。**

## 4. 组件职责矩阵

| 组件 | 负责什么 | 不负责什么 | 能否被 Jev 替代 |
|---|---|---|---|
| FrugalRAG 检索 | 本地 E5 向量 + BM25 融合、课程软过滤、余弦阈值，产出候选集 | 不做判断、不生成、不出最终结论 | ❌ 不可替代（Jev 不检索）；仅可能在召回后充当重排打分器 |
| 规则引擎 | 确定性约束（先修、学分、课程边界等）裁定 | 不做语义判断 | ❌ 不可替代（概率模型不如确定性规则可审计） |
| 解析式 review_policy（`analytic_review_action`） | 解析式审查判定，capture 100%、零训练零成本 | 不做开放式语义判断 | ❌ 不可替代，引入 Jev 为负收益 |
| 讯飞 LLM（+ DeepSeek 兜底） | 文本生成、解释、对话式产出 | 不做高并发类型化判断；单位成本高 | ⚠️ 其**判断类子问题**可被 Jev 分流，但生成能力不可替代 |
| Jev | 类型化判断（Choice/Score/Noul），并行求值、低延迟、低单价、可校准 | 不检索、不生成文本、不可自托管、决策不透明 | — |

## 5. 逐节点适配评估

| 节点 | 判断型 / 生成型 | 适配度 | 理由 |
|---|---|---|---|
| triage | 判断型 | **高** | 分流分类是典型 Choice；单次 state 可封装；并行求值契合；70–500 ms 优于现链路 |
| coordinator | 判断型（调度） | **中** | 子集群选择可作 Score/Choice 辅助打分；但编排依赖状态机与全局一致性，Jev 单次无状态，不应接管编排 |
| diagnostician | 生成型 | **不适用** | 需产出诊断报告文本与归因解释 |
| planner | 生成型 | **不适用** | 需产出学习计划文本 |
| retriever | 检索型 | **中（重排）/ 不适用（检索）** | 检索本体不适用；仅可在召回后做重排打分（官方推荐用例含 search reranking），须与现行融合口径做对照，属 P2 |
| generator_cluster | 生成型 | **不适用** | 核心职责就是生成 |
| assessor | 判断型 | **高** | Score 原语直接对应评分量程；ECE 0.07 可用于置信分级 |
| critic | 判断型 | **高** | Noul 是/否 + 概率天然对应「是否通过 / 是否合规」 |
| evidence_check | 判断型 | **高** | 「claim 是否有证据支撑」= Noul；返回概率即可做阈值分流 |
| quality_gate | 判断型 | **不适用** | 已有解析式 `analytic_review_action`，capture 100%、零训练零成本；换用 Jev 为负收益 |
| path_planner | 判断型（约束规划） | **中** | 候选路径打分可用 Score；路径合法性由规则引擎裁定，Jev 只宜辅助排序 |

补充：`discipline_gate`（**非上述 11 节点之一**）——判断型，**不适用**：确定性规则比概率模型更可审计。

## 6. 成本模型

试算：单次判断 state ≈ 1000 token → 一轮 30 题 × 3 = **90 次判断 ≈ 9 万 token** → 9 万 × $0.042/1M ≈ **$0.0038 / 轮**。新户 $5 首充 ≈ **1.19 亿 token**，按上述规模相当于约 1300 轮实训。

**结论：成本不构成决策理由。** 单价低到在当前使用规模下可忽略；因此选型判断只应依据**能力边界、可复现性、可审计性与判断质量**，不得以「更省 token」为主张。

## 7. 风险清单

**① 不可自托管**
- *影响*：破坏「离线可复现、断网可跑」基座，引入外部依赖与可用性不确定性；早期访问期可用性不可保证
- *缓解*：定位为实验目录内的旁路试点，永不进入交付链路；离线路线仍由本地链承担，试点结果不得写入任何对外口径

**② 托管模型静默更新**
- *影响*：同输入不同输出，直接违反「口径先行 / 证据先行」，历史实验不可复现
- *缓解*：试点须记录调用时间戳、模型版本标识（若服务方提供）与原始响应落盘，作为**仅追加**工件；Jev 输出一律不参与对外数字

**③ 自评 67.8% 准确率对教育评判不足**
- *影响*：误判评分或证据结论会污染学习路径与考核结果
- *缓解*：设置信阈值三级升级——**高置信自动 / 中置信复核 / 低置信转人工**；阈值需实验标定（具体阈值**未验证**）

**④ 黑盒不透明（无权重、决策不可解释）**
- *影响*：教育场景需可追溯，学生申诉与内部审计无法回答「为什么这样判」
- *缓解*：判定必须留存 state 原文 + 概率值 + 可读理由字段，任一自动结论可回溯到输入；关键判定保留规则引擎兜底

## 8. 建议路线

**P0（现在，0 代码）**
- 固化结论：**Jev 不进主线、不替代 FrugalRAG、不接管 quality_gate / discipline_gate**，写入技术选型记录
- 同步修正「为省 token 才选 FrugalRAG」的错误叙事（实测收益在质量侧）
- **本阶段不动任何代码**

**P1（可做——前置条件齐备时）**
- 旁路离线对照实验，只覆盖 triage / critic / evidence_check / assessor
- 前置条件：① 取得 Jev API key；② 用户明确授权；③ **必须旁路**——新增脚本只读既有 state 与题集，输出落盘到独立 artifacts 目录，不修改 `py-server/` 任何文件、不接入运行链路；④ 实验口径可溯源：题集来源为 `py-server/experiments/queries.json`（28 条，对应 benchmark 实验1 的 28 查询）；benchmark 实验2 的 30 题×3 属于另一套题集，两者不可混用；试点须显式声明所用题集与来源，禁止以有放回重复采样冒充口径对齐；seed 沿用 20260719
- 验收：四节点判断一致性 + 置信分级可用性

**P2（延后，依赖 P1 结果）**
- retriever 重排打分对照、path_planner 候选排序辅助；仅在 P1 证明判断质量与置信分级可用时才评估

**明确不做**
- 用 Jev 替换 FrugalRAG（类别错误）
- 用 Jev 接管 quality_gate / discipline_gate
- 把 Jev 输出写进对外材料数字

## 9. 待确认问题

1. 试点目标是验证「判断型节点可换成更便宜更快的模型」，还是验证「召回后重排能否再提质量」？两者验收标准不同。
2. 是否已获得可用 API key 与预算授权（$5 首充由项目还是个人承担）？
3. **试点输入集口径（已知约束，非待定项）**：题池为 `py-server/experiments/queries.json`，共 **28 条**；seed `20260719` 下若按 30 采样将有放回，实测 distinct 仅 19、重复 11 条，样本被重复项加权且结论不可复现。因此试点须显式声明所用题集与来源，不得把「30 题×3」当作同一题集复用。
4. 「离线可复现」是否为**硬约束**？若为硬约束，Jev 是否只允许停留在实验目录、永不进入交付链路？
5. 若 P1 结论为「判断质量不及现有解析式 / 规则」，是否接受直接终止、不进入 P2？

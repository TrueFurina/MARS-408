## 一、D-1 处置：对照实验三个数据端点加鉴权

### 1.1 先复现，再动手（实测证据）

改之前用探针实测，确认三条都能被无凭据访问（均为 200）：

```
[step] 无 token 写入 __probe_stu__ -> 200
[probe] 无 token 读 report/__probe_stu__（IDOR 复现） -> 200 user_id=__probe_stu__
[probe] 无 token 读 class-report（含姓名） -> 200 students=[('__probe_stu__', '探针学生')]
```

### 1.2 我为什么修正了推荐方案

上一轮的**方案 A** 是「两个读接口都挂 `Depends(require_teacher_or_demo_open)`」。
实测后这条需要修正，依据是三个事实：

| 事实 | 出处 | 后果 |
| --- | --- | --- |
| `/report/{user_id}` 是**学生查自己**的接口，学生页硬编码调 `/literacy/report/demo` | `src/views/LiteracyAssessmentView.vue:57` | 挂教师鉴权会把学生页打成 403 |
| 演示开关 `NETLEARN_DEMO_TEACHER_OPEN` **在 `.env` 里并未设置** | `.env`（仅 29 个键，无此键） | 学生页会被 403，且无人会想到去开这个开关 |
| 该开关一旦作用于个人报告，演示环境里任何 demo 账号都能按学号枚举读数 | 设计推理 | 等于把刚关掉的 IDOR 原样放回 |

因此改为**按语义分别处置**（这更贴合推荐方案的意图——"不打断课堂"）：

| 端点 | 处置 | 理由 |
| --- | --- | --- |
| `GET /questions` | **保持公开** | 只读题库、无学生数据、无写入；学生在取到题目时必须可用 |
| `POST /submit` | `Depends(get_current_user)` | 拦住「匿名第三方以任意学号写入研究原始数据」 |
| `GET /report/{uid}` | `Depends(require_self_or_teacher)`（**新增依赖**） | 本人 / 教师 / 管理员；**不接演示开关**（见上表） |
| `POST /class-report` | `Depends(require_teacher_or_demo_open)` | 与 `api/teacher.py` 教师端点同口径 |

新增依赖写在 `shared/auth.py`，`user_id` 由 FastAPI 从同名路径参数自动注入，
调用方无需显式传参。

### 1.3 刻意保持不变

`_resolve_submitter_uid` 的「**请求体 user_id 优先于 token**」语义**原样保留**。
理由（代码注释里原有，属课堂流程的硬约束）：全班共用 demo 账号登录时 token sub
一律是 `demo`，若 token 优先，全班提交会互相覆盖（并发试测实锤过一次）。

权限与身份归属**刻意分离**：闸门管「谁有权提交」，该函数只管「记到谁名下」。
混在一起会让两者互相污染。

### 1.4 收紧后的实测契约（13 条，全部符合设计）

```
submit 无 token                                          -> 401
submit 带 student token                                  -> 200
submit 带 student token + 伪造他人 user_id                 -> 200   ← 见「残留风险」
report/self 无 token                                     -> 401
report/self 带本人 token                                  -> 200
report/other 带他人 student token                         -> 403   ← IDOR 关闭
report/other 带 teacher token                            -> 200
class-report 无 token                                    -> 401
class-report 带 student token（开关关闭）                   -> 403
class-report 带 teacher token                            -> 200
class-report 带 student token（开关打开）                   -> 200   ← 演示放宽
report/other 带 student token（开关打开）                   -> 403   ← 刻意不放宽
questions 无 token                                       -> 200
```

### 1.5 ⚠️ 残留风险（本次未解，请知悉）

**已登录的 demo 账号仍可替他人提交**（上表第 3 行，返回 200）。
这不是本次改动引入的，而是「全班共用账号」模式的**固有代价**——
服务端无法把自报的学号与登录身份对应起来，因此无法做归属校验。

- 本次改动把它从「**匿名即可改**」收紧为「**须持有效凭据才可改**」，但没根治。
- 根治需为每名学生发独立账号；即便如此，第 3 行的行为仍会被拒绝，但学生端
  硬编码的 `/report/demo` 也要随之改成读自己的报告——属另一条线，不在本次范围。

### 1.6 变异验证（逐个摘掉依赖，确认断言真的会红）

| 变异 | 结果 |
| --- | --- |
| 摘掉 `/submit` 的 `get_current_user` | 2 条 401 断言红；行为断言不受影响 |
| 摘掉 `/report` 的 `require_self_or_teacher` | 3 条拒绝断言红；3 条放行断言仍绿 |
| 摘掉 `/class-report` 的 `require_teacher_or_demo_open` | 3 条拒绝断言红 |

三处均已还原，`grep 变异验证` 残留为 0，随后 5 条不变量 + 35 条 literacy 断言全绿。

### 1.7 一个必须写下来的坑：测试替身会让鉴权断言「假绿」

`tests/conftest.py` 有一个 **autouse** 的 `mock_auth`，把 `get_current_user`
顶成一个 **admin** 假用户，使所有请求无条件通过鉴权。

契约测试若不关掉它，断言 401/403 会**全部失败**；而更危险的是——
一旦有人把断言改写成「期望 200」，它会**永远绿着**，完全测不到
「依赖是否真的挂在路由上」。

故契约测试用项目既有 opt-out fixture `no_mock_auth` 关闭替身
（先例：`tests/test_api_contract_comprehensive.py::test_me_requires_auth`）。
契约测试坚持走 HTTP 层而非直接调用依赖函数，正是因为要证明**挂载**这件事本身
（直接单测依赖无法证明它挂在路由上）。

### 🔴 D-5. 「N 节点」不是漂移，而是两种定义

本轮**没有**做 `10 节点 → 11 节点` 的批量替换，理由如下：

`10 节点` 仍出现在 10+ 处：

```
src/components/FrugalRAGPanel.vue:35,129        py-server/agents/triage.py:4
src/components/LangGraphFlow.vue:3,105          py-server/api/langgraph.py:42
src/views/EngineView.vue:16,199,216             py-server/engines/algorithm_factory.py:13
src/views/ShowcaseView.vue:85                   py-server/tools/generate_demo_ppt.py:98,113,189
```

而 `agents/triage.py:4` 的注释写着：

> 作用：在完整 **10 节点流水线之前**，用轻量规则判断任务风险等级。

`api/langgraph.py:42` 同样写「高风险请求进入完整 **10 节点**流水线 + 三评审」。

也就是说，作者把 `Triage` 视为**流水线之外的前置路由**，因此：

- 「**11 节点**」= 编译图中业务节点总数（`agents/graph.py` 实有 11 条 `add_node`，含 Triage）；
- 「**10 节点**」= 流水线本体（不含前置路由 Triage）。

两者**都能自洽**。故这不是"数字写错"，而是**同一名称指两个对象**。
批量把 10 改成 11 可能把原本正确的表述改错。

**需要你一句话裁决**（三选一）：
- **(a) 以图为准**：统一说「11 节点 LangGraph」→ 我把那 10+ 处一并改掉（机械操作，可验证）；
- **(b) 以流水线为准**：description 改回「10 节点流水线（+ Triage 分级路由）」→
  **需要同时改掉上一轮那条守护断言**（它现在等价于方案 a）；
- **(c) 两个都说清**：如「11 节点 LangGraph（含 Triage 分级路由）/ 10 节点主流水线」，
  最准确但字数变长。

> 说明：上一轮我把 description 的「10 节点」改成「11 节点」，当时的判断是
> 「注释未随新增 Triage 同步」。本轮读到 `triage.py` 的原文后，这个判断需要被
> 修正为**两种定义并存**。这是我本轮推翻自己上一轮结论的地方，特此标注。

## 四、D-3 状态：评估后**不做**（有据）

`openapi.json` 快照落后 4 个 `/api/cn-distinction` 路径（223 vs 227）。评估结论：

1. **前端完全不调用 `cn-distinction`**（`grep -rn "cn-distinction" src/` 为空），
   故这 4 个缺失路径对 `src/types/api.generated.ts` 的下游影响为**零**。
2. 快照里真正的**对外契约**部分（`info.description`）已由第 5 条守护断言锁死，
   并与实时 `app.openapi()` 逐字比对一致（实测 `description 一致: True`）。
3. 完整同步要重写 2900+ 行的生成物（`node_modules` 是 junction，宽 diff 在本机
   有假删除史），**收益为零、风险非零**。

**结论**：属文档新鲜度问题而非功能问题，记录在案，等有前端联调窗口时再一并做。

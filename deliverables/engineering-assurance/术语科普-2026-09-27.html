0一句话版本：这几轮我到底在干嘛

你给我的项目代码，长期积累出三类隐患：结构太乱（一个文件干六件事）、 偷偷越权（谁都能直接抓数据库）、测试不可信（绿灯不代表没问题）。 我做的四件事，每一件都必须能被证明，而不是我说"改好了"就算数：

  • 拆大文件 —— 让每个文件只干一件事（对应术语：上帝文件、装配层、分层）。
  • 堵越权 —— 让所有读写都必须经过规定的门口（对应：委托、单一真值源）。
  • 证明没改坏 —— 拆之前先冻一份"存档"，拆完逐项对账（对应：基线快照、差分）。
  • 证明检查真有用 —— 故意把代码改错，看检查能不能抓住（对应：变异验证）。

第 3、4 条是我这几轮花时间最多的地方。原因很现实：拆文件这类改动最大的风险不是报错，而是悄悄出错还能跑过去。

1术语对照表（按六类分）

1.1 架构评审类 评估结构问题

术语大白话为什么会出现
M-1 ~ M-5评审报告里给问题编的号，方便点名（如"M-2 已修"）没有编号，说"那个存储的问题"就说不清是哪个
Major / Minor严重程度分级：Major 影响正确性和可维护性，Minor 是整洁度决定先修哪个，不是所有问题都等值
上帝文件一个文件承担太多职责，谁都不敢动main.py 原本 882 行同时管启动、限流、报错、路由
装配层只负责"把零件装起来"的最外层文件装配代码最容易变，应该让它薄到一眼看完
分层（API → services → db）规定"谁能直接碰谁"：接口层不许直接抓数据库否则同一个业务规则会在 27 个文件里各写一遍
单一真值源同一件事只允许在一个地方定义，其他地方只能引用防止"改了一处、漏了另一处"的数字漂移
越级访问不该碰底层的地方直接去抓底层连接、锁像前台直接进金库开保险箱，出事没人管得住

1.2 验证方法类 证明"真的没改坏"

术语大白话为什么会出现
基线快照动手之前，先把现状存一份"指纹存档"没有存档，改完就无从对比"是不是真的一样"
差分比对改完之后，逐个项目和存档对账只统计"条目数对不对"抓不到细节（实测 1892 条变 1885 条时节点数完全没变）
行为探针跑一段固定操作序列，把每步结果记下来当存档函数不能靠"指纹"比（见 2.1）
机验脚本 / 守门脚本一条命令跑完，全自动判定对错的小程序让结论可复现，不依赖"我记得"
变异验证故意把代码改坏，看检查报不报警不报错就说明检查是摆设（见 2.3）
静默失败 / 响亮失败静默＝不报错但结果错了；响亮＝直接崩静默失败危险得多，所以变异要挑"安静地变错"
AST 比对不看文本长相，直接比较"代码结构"是否一致比较列表有没有漏项、顺序有没有变

1.3 Python 导入与对象类 今天事故的主因

术语大白话为什么会出现
模块（module）一个 .py 文件在内存里的"化身"，全局只有一份这个"只有一份"的假设今天被打破了
sys.modulesPython 的"已加载模块登记处"，按名字缓存谁改了这个登记处，谁就改变了所有人的认知
类身份分裂同一个文件被加载两次 → 内存里出现两个"同名类"，互相不认识今天测试变红的真凶（见 2.2）
PEP 562 / __getattr__让模块支持"用到时才去查"的动态属性我用它实现"动态委托"（见 2.1）
动态委托门面自己不存东西，每次被问就转给真正的负责人避免拿到过期副本
monkeypatch测试期间临时替换某个函数/属性，用完自动还原测试隔离的基础手段
快照式绑定from 模块 import 函数 会把"当时的那个函数"钉在你手上之后再替换原件，你手上还是旧的（见 2.1）

1.4 测试框架语义类 为什么"绿灯"会骗人

术语大白话为什么会出现
xfail"我预期它会失败"的标记功能没做完/依赖外部服务时的常规做法
XPASS标了"预期失败"，结果它通过了关键陷阱，见 2.2
strict=True"如果它意外通过，就判整个测试失败"本意是提醒"该更新标记了"，结果造成 CI 必红
xpassed / xfailed / skipped意外通过 / 如预期失败 / 跳过，三种都不算真失败读结果时要分清这三个数字
collection error测试还没开始跑，光"收集名单"就炸了今天另一个真问题：一个文件 import 失败 → 36 个用例从未跑过
顺序依赖单独跑和一起跑，结果不一样说明测试之间互相污染

1.5 工程治理类 防止"我自己觉得没问题"

术语大白话为什么会出现
门禁 / pre-commit 钩子提交代码时自动跑的检查，不合格直接拒绝提交本项目有 6 道：密钥扫描、诚实口径、数字口径、结构、ruff、测试文件
fail-closed拿不准时"拒绝"而不是"放行"安全类检查的正确姿势
白名单豁免给特定文件/规则开例外，其余照查教学语料里的 AES 知识点被误判成密钥 → 只豁免那一条规则
覆盖率门槛"被测试跑到的代码比例"低于某个数就判失败项目设 54%，实际 52.32%（唯一的 NO-GO 阻塞）
CI 红灯持续集成流水线里的失败状态红灯 = 这次改动不能合并

1.6 存储与并发类 数据别写坏

术语大白话为什么会出现
连接（connection）通往数据库的一条通道开太多会互相打架
锁 / RLock同一时间只允许一个人写的"排队规矩"；RLock 允许自己重复进防止两个请求同时写同一行导致损坏
锁域"这把锁负责哪个范围"以前三个数据库文件各有一把互不知情的锁
WALSQLite 的一种日志模式，读写可以并行，更抗崩连接参数统一时一并确认
幂等建表"建表"这句话执行一百次，效果和执行一次一样每次启动都建表而不出错
越级取连接绕过规定的封装，直接抓底层连接跑自己的 SQL拆域时的主要清理对象

2三个最容易误解的机制

2.1 "委托"和"复制"长得像，行为完全不同

静态导入 = 复制一份引用

from a import f 会把"此刻的 f"钉在手上。

之后别人替换了 a 里的 f，你手上仍然是旧的。

危险点：不报错。补丁静默失效，你以为在测降级路径，实际在走真实逻辑。

动态委托 = 每次重新问

模块里不存东西，访问时才 return getattr(真身, name)。

别人一换，你立刻跟上。

这就是 PEP 562 模块级 __getattr__ 的用途。

这不是洁癖：今天这个问题真实发生了 —— services/user_service 当初是静态重导出， 导致一个"数据库故障降级"的测试永远测不到真实分支（它的断言一直失败得很稳定，我一度以为是它写错了）。

2.2 同一个文件被加载两次 = 两个类

Python 用 sys.modules 这个"登记处"保证一个模块只有一份。但如果有人用 importlib.util.spec_from_file_location 另外加载一份并塞进登记处，就会出现两个同名类。

  • 测试框架给原件打补丁 → 业务代码拿到副本，没被打补丁 → 走了真实逻辑。
  • 两个类互相不认：isinstance 判断为假、try/except 捕不到异常。
  • 这不是我瞎猜，Python 官方 PEP 499 明确列了这些后果（见第 3 节）。

2.3 为什么"检查通过"不够，还要"故意改坏"

假设我写了一个检查脚本，它打印"全部通过"。这有两种可能：代码真的没问题， 或者检查本身写错了、什么都没查。两者输出一模一样。

破解办法只有一个：故意把代码改错一次，看检查会不会报警。会报警 → 检查有效；不报警 → 检查是摆设。 这在软件工程里有正式名字：变异测试 / mutation testing（1971 年提出，专门用来评估"测试到底有没有用"）。

3网上资料清单

3.1 Python 对象与导入机制

  • PEP 562 – Module __getattr__ and __dir__ 已核验
    我用的"动态委托"就是这一条提案。官方文档，短、有例子。想搞懂 __getattr__ 为什么能解决"拿到过期副本"，看这个。
  • Python 语言参考 · Data model（模块 __getattr__ 一节） 已核验
    权威定义：模块级 __getattr__ 只在"正常查找找不到"时才被调用。解释了很多"为什么我这样写没生效"。
  • PEP 499 – 两个模块实例带来的混乱 已核验
    今天事故的官方背书。它逐条列出"同一模块存在两个实例"的后果：注册表分裂、哨兵值失效、类重复定义导致 isinstance/except 失灵。
  • Python's importlib: Dynamic Imports and Module Reloading（PyCon UK） 已核验
    讲清 sys.modules 缓存、reload() 为什么"改了文件也不生效" —— 和我们的类身份分裂是同一类问题的不同侧面。

3.2 测试框架语义（pytest）

  • pytest 官方 · skip 与 xfail 已核验
    XPASS 的官方定义，以及 strict=True 的含义："意外通过就判整个测试失败"。读懂这一节，今天那块红灯逻辑你就完全明白了。
  • pytest 中文文档 · skip 与 xfail 已核验
    同上，中文镜像，读起来更省力。
  • pytest 中文文档 · API 参考（xfail 的 strict 参数） 已核验
    原文说明：strict=False 时 xfail/xpass 都不让整个测试失败；strict=True 时意外通过会让测试失败。

3.3 测试有效性（变异测试）

  • Mutation Testing Theory（卢森堡大学 变异测试研究目录） 已核验
    学术侧的定义：变异体（mutant）、被杀死（killed）、存活（survived）、变异得分。想要严谨表述就引这里。
  • Wikipedia · Mutation testing 已核验
    历史与全貌最全，含"测试的测试（test of the tests）"这一说法的由来。
  • Mutation Testing: A Practical Overview（实践向） 已核验
    偏工程视角，有具体例子（a == b 改成 a != b 却没测试报警）。想动手试就从这个开始。

3.4 覆盖率与质量门禁

  • How to Measure Code Coverage with pytest-cov 已核验
    解释本项目覆盖率门槛怎么来的：fail_under = 80 这类配置一旦低于阈值，pytest 直接以非零码退出，从而让 CI 失败。
  • pytest-cov 完整指南（阈值设定经验） 已核验
    讲几条实用经验：门槛应设在"比现状略低"然后逐步抬高；不要设 100%；不要为了数字写无断言的测试。跟本项目 54% 门槛的处境直接相关。
  • coverage.py 官方文档
    底层工具本身（pytest-cov 只是它的插件）。要查具体配置项（exclude、branch、parallel）来这里。

3.5 顺带相关的官方入口

  • pre-commit 官方站
    "提交前自动跑检查"这套机制的框架。本项目 6 道门禁就是挂在这一套钩子上。
  • SQLite · Write-Ahead Logging（WAL）
    理解"为什么连接参数要统一、为什么并发写要排队"的原始说明。
  • Starlette · Middleware
    FastAPI 底层框架。说明中间件的"洋葱式"包装顺序 —— 这就是我强调"注册顺序不能乱"的依据。

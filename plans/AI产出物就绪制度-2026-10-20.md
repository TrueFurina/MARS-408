# AI 产出物就绪制度（2026-10-20）

> 来源：REA #34 / #39。适用对象：本仓库里由 AI 会话产出的任何"完成"声明——
> 代码、文档、报告、数据、截图、PPT。
> 一句话：**AI 只能声明"可验证的完成"，"人就绪"（能拿去用/能对外发）只能由人声明。**

---

## 一、为什么要写这个

本仓库同时有多个 AI 会话在改（共享 `config.py` / `run.py` / `package.json`），
历史事故形态高度一致：**产出物在，但没人验证过它是否可用**；或者反过来，
**验证过了，但产物没落到仓库**（下次会话从零开始）。

两种都会让"已完成"变成噪声。本制度把"完成"拆成可判定的三档，并要求落点。

## 二、三档判定（缺一档不得越级声明）

| 档 | 名称 | 判据（机器可判） | 谁能声明 |
|---|---|---|---|
| L1 | **代码在位** | 文件在仓库、`git status` 干净或已提交；能被 import / 被引用 | AI |
| L2 | **演练通过** | 有测试或脚本**实际跑过**，附命令 + 结果计数（如 `12 passed`）+ 退出码 0 | AI |
| L3 | **人就绪** | 人确认过：口径能对外说、数据能引用、界面能演示 | **仅人** |

- 声明 L2 必须**贴出复跑命令**与**真实输出摘要**；贴不出 = 只是 L1。
- AI **不得**声明 L3，也不得用"应该可以了/基本没问题/已优化"这类措辞替代判据。
- 反向也成立：L2 通过不代表 L3 —— 例如测试绿但文案含未验证成效数字，仍是"不就绪"。

## 三、产出物落点规则（防"下次从零开始"）

| 产出物 | 必须落在 | 附带要求 |
|---|---|---|
| 代码 | 对应仓库目录 + commit | commit message 带实践编号（如 `M05 / REA #15`） |
| 分析/调研文档 | `deliverables/` 或 `plans/`（**不进仓库根**） | 文首写"结论先行"，文末写证据路径 |
| 实验结论 | `experiments/<名>/`（四件套） | 见 `experiments/README.md` |
| 一次性验证输出 | 不要入库 | 贴进对话或 commit message 即可 |
| 交付/汇报材料 | `deliverables/` | 数字须能指向 registry / 测量脚本 |

**硬规则**：任何"已完成"的产出物，要么有 commit，要么有文件路径；两样都没有的，
按"未产出"处理，不得计入进度。

## 四、会话交接（多会话并发时的最低要求）

每次会话结束前，在 `plans/current.md` 的闭环判据表里更新状态，并写清：

1. 我改了什么（文件 + 一行意图）
2. 我**验证**了什么（命令 + 计数）；**没验证**什么（必须显式列出）
3. 下一个会话该从哪里起手（不要写"继续优化"，要写"跑 X 命令，看 Y 是否绿"）

**禁止**：把"我计划要做"写成"已完成"；把 mock 通过的路径写成"端到端打通"；
把合成环境结论写成真实效果。

## 五、与既有门禁的关系

| 制度要求 | 已有机器保障 |
|---|---|
| L2 可复跑 | `npm run verify` / `python scripts/doctor.py` / CI 六路工作流 |
| 文档不吹牛 | `scripts/check_error_wording.py` + README 三档口径表 |
| 数字可追溯 | `pilot_evidence_report` 取证闸 + `experiments/` 四件套 |
| 提交前快检 | `pre-commit`（7 道）+ `pre-push`（5 道，见 `scripts/pre-commit/`） |

制度不替代门禁：**门禁能判的，制度不重复要求人手检查**；门禁判不了的
（口径能不能对外说、数据能不能引用），才是本制度存在的理由。
